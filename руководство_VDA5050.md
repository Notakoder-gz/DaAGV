# Руководство клиента VDA 5050: примеры запросов

Документ описывает MQTT-команды управления роботом по протоколу VDA 5050 v3.0.0.1, которые были успешно выполнены на стенде. Каждый раздел содержит описание сценария, MQTT-топик и точную JSON-полезную нагрузку, проверенную на роботе.

## 1. Транспорт и адресация

- Брокер: MQTT (например, `mosquitto`), QoS публикации — на усмотрение клиента (рекомендуется `1`).
- Формат топиков:
  - Ордеры: `vda5050/v3/{manufacturer}/{serialNumber}/order`
  - Мгновенные действия: `vda5050/v3/{manufacturer}/{serialNumber}/instantActions`
- Топики для подписки (мониторинг состояния робота):
  - `vda5050/v3/{manufacturer}/{serialNumber}/state` — основной поток статусов (ордер, action, node, ошибки).
  - `vda5050/v3/{manufacturer}/{serialNumber}/connection` — `ONLINE` / `OFFLINE` / `HIBERNATING`.
  - `vda5050/v3/{manufacturer}/{serialNumber}/visualization` — текущая поза робота (x, y, theta).

В примерах ниже используется `manufacturer = zgreat`. Полный публикуемый топик имеет вид: `vda5050/v3/zgreat/{serialNumber}/order`.

## 2. Что необходимо подставить перед отправкой

Каждое сообщение клиент должен заполнить актуальными значениями:

| Поле | Где | Что подставить |
|------|-----|----------------|
| `manufacturer` | заголовок | значение из паспорта робота (в примерах — `zgreat`) |
| `serialNumber` | заголовок и топик | серийный номер вашего робота |
| `headerId` | заголовок | монотонно растущий счётчик исходящих сообщений |
| `timestamp` | заголовок | текущее время в ISO-8601 с таймзоной |
| `orderId` | ордер | уникальный идентификатор ордера; рекомендуется числовая строка |
| `orderUpdateId` | ордер | `0` для нового ордера, `+1` при обновлении того же `orderId` |
| `actionId` | действия | уникальный идентификатор действия в рамках ордера |
| `mapId` | `nodePosition` | идентификатор активной карты робота |
| `nodeId` / `edgeId` | nodes/edges | идентификаторы из карты робота |

Примеры полезной нагрузки сохранены с теми значениями `serialNumber` и `mapId`, на которых проводилось тестирование (`1`, `37`, `111`; карты `perekresto@DEMO`, `testmap@test`, либо `null`). Перед отправкой замените их на значения вашего стенда.

## 3. Общие правила

- `version` в примерах — `v3.0.0.1`. Используйте версию, согласованную с вендором робота.
- В заголовке каждого сообщения должны присутствовать: `headerId`, `timestamp`, `version`, `manufacturer`, `serialNumber`.
- Перед каждой отправкой обновляйте `headerId`, `timestamp`, а в ордерах — `orderId` (или `orderUpdateId`) и `actionId`.
- Нумерация в массивах `nodes` / `edges`: `sequenceId` чередуется — нечётные значения у edge, чётные у node, начиная с `0`.
- Поле `released: true` означает, что робот может выполнять данный node/edge без дополнительного подтверждения (running release horizon = full).
- `orientation` на edge задаётся в радианах: `0` — движение вилами вперёд, `π` (`3.141592653589793`) — вилами назад.
- `blockingType` действия:
  - `HARD` — действие блокирует движение и другие действия;
  - `SOFT` — допускается параллельная навигация;
  - `NONE` — действие не блокирует.

### Кейс 3.1 Особые соглашения вендора (текущая прошивка)

- `stopPause` ставит робота на паузу, `startPause` возобновляет движение (см. кейс 4).
- Для подъёма/опускания вил используется действие `fork` с параметрами `type=upDown`, `upDownType=liftingLevel`, `level=1` (поднять) или `level=0` (опустить). При операциях с паллетой дополнительно задаётся `taskType=4` (взятие) или `taskType=5` (выгрузка).
- Перед подбором/выгрузкой паллеты на финальный edge добавляется действие `precisePositioning` с пустыми параметрами для точного позиционирования.
- Действие `sensorData` принимает параметр `type` в виде числового кода (например, `"9"`), либо строкового имени (`lidar` / `photo` / `fork`) — зависит от прошивки робота.

## 5. Контроль выполнения

После отправки ордера или мгновенного действия следите за топиком `state` робота. Ключевые признаки успешного выполнения:

- `state.orderId` совпадает с отправленным `orderId`, `state.orderUpdateId` соответствует ожидаемому.
- `state.nodeStates[]` и `state.edgeStates[]` уменьшаются по мере прохождения маршрута.
- Для каждого действия в `state.actionStates[]` наблюдается переход `WAITING → INITIALIZING → RUNNING → FINISHED` (либо `FAILED` при ошибке).
- При ошибках заполняется массив `state.errors[]` с `errorType`, `errorLevel` и описанием.
- Для пауз: после `stopPause` поле `state.paused = true`; после `startPause` — `false`.
- Для зарядки: `state.batteryState.charging = true` при активной зарядке.
- Для режима ожидания: в топике `connection` — `HIBERNATING`, публикация `state` приостанавливается до `stopHibernation`.
